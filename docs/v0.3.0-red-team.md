# v0.3.0 red-team review

Status: engineering review complete; independent security review pending.

## 1. Can a PR modify its contract to pass?

**Yes, unless the workflow treats the PR contract as untrusted.** A workflow that hashes the PR's own contract and immediately accepts that digest provides no protection. The safe examples retrieve the contract from the base commit, compute its digest from that trusted copy, and pass both to ACL. A digest mismatch is `UNVERIFIABLE` before contract parsing.

## 2. Can contract hash pinning be bypassed?

The CLI compares SHA-256 over exact bytes before parsing and does not provide an ignore/fallback path. The practical bypass is operational: supply an attacker-controlled expected digest, run a modified verifier/action, or compromise the runner. Documentation therefore requires a protected digest source and immutable action pin for higher assurance.

## 3. Can allow-listed Python still execute malicious local code?

**Yes.** `python -m pytest`, build backends, plugins, imports, and scripts can execute repository code. The executable allowlist is not a sandbox. Static-only mode avoids command assertions; full mode requires disposable, least-privilege isolation.

## 4. Can reports leak stdout/stderr secrets?

Command stdout/stderr is captured only to prevent console leakage and is not inserted into reports. Tests assert that marker secrets printed to both streams are absent. Reports may still reveal task IDs, paths, repository identity, assertion messages, or contract literals. Secrets must not be placed in those fields.

## 5. Can the GitHub Action expose secrets to a fork PR?

The documented PR workflows use `pull_request`, `contents: read`, no secrets, and no `pull_request_target`. Users can still write unsafe workflows. ACL cannot prevent a repository owner from granting extra permissions; the secure examples and threat model make the boundary explicit.

## 6. Can the in-toto statement be mistaken for a formal attestation?

**Yes.** The format can look authoritative. The predicate and documentation repeatedly label it experimental and unsigned unless processed by an external attestation system. It uses a custom predicate URI and does not claim SLSA, GitHub, or standards-body certification.

## 7. Can a signed report be mistaken for correct software?

**Yes.** A signature establishes issuer/artifact integrity under the signing system, not semantic correctness, security, contract completeness, or product value. The report and predicate contain explicit limitations, and GitHub attestation guidance is separated from ACL status.

## 8. Can contract authoring cost more than manual review?

**Yes.** This is an unresolved product risk. The external protocol records authoring time, line count, CI overhead, maintenance willingness, and review-time effects. A median authoring time above 30 minutes is a project stopping condition unless a clearly documented high-value use case justifies it.

## 9. Is ACL only reformatting tests?

Sometimes the contract may add little beyond CI. ACL's distinct contribution is to bind a specific completion claim to required evidence, represent missing evidence as `UNVERIFIABLE`, pin contract integrity, and emit reviewer provenance. If ordinary CI already provides the same clarity with lower maintenance cost, the simpler CI process should be preferred.

## 10. Do adjacent platforms already provide the same function?

Adjacent tools cover runtime tracing, operation evidence, audit records, provenance, attestations, policy enforcement, and CI. There is meaningful overlap. ACL's narrow claim is repository-level acceptance evidence for coding-agent tasks; it must not claim an empty competitive field or broader standard status. External pilots will test whether the narrow layer is useful rather than duplicative.

## 11. Will external maintainers maintain contracts?

Unknown. No non-author maintainer has completed a pilot. Maintenance willingness is a required metric, and three non-author repository integrations are required before claiming adoption progress.

## 12. Is there a simpler process than a ledger?

Often yes: a checklist, existing CI required checks, pull-request template, or reviewer policy may be enough. The adoption guide includes removal instructions. ACL should be used only when explicit four-state evidence, contract integrity, reusable reports, or attestation handoff justify the additional contract.

## Accepted limitations and resulting position

The red-team review narrows the position rather than dismissing valid criticism:

- ACL is acceptance evidence, not execution security.
- Trusted Contract Mode is byte integrity, not sandboxing.
- Static-only mode sacrifices command evidence and correctly returns `UNVERIFIABLE`.
- The in-toto surface is a structured statement, not proof.
- Existing CI may be the better tool for simple repositories.
- External value remains unproven until real maintainer data exists.
