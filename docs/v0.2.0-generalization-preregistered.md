## Research question

In a different benchmark family and agent implementation, does treating every submitted/generated patch as `COMPLETED` still produce a materially high rate of completion labels unsupported by the available executable oracle, and can the same four-state ledger represent that evidence without changing its semantics?

## Operational definitions

- Generated/submitted completion claim: one item counted in `submitted_instances` and `completed_instances` by the fixed source.
- Oracle-supported claim: one item counted in `resolved_instances`.
- Oracle-unsupported claim: a completed claim counted in `unresolved_instances`.
- Missing/incomplete execution: `unstopped_instances` or a mismatch among source count identities.
- Baseline policy: every completed/submitted claim receives the label `COMPLETED`.
- Contract policy: only a claim backed by the source's resolved executable result receives `SUPPORTED`; unresolved claims receive `FAILED`; incomplete or non-reconcilable evidence receives `UNVERIFIABLE`; absent claims receive `NO_CLAIM`.

The oracle is treated as scoped executable evidence, not ground truth for user satisfaction or semantic correctness.

## Hypotheses

### H1

The fixed independent source has:

1. at least 50 completed/generated claims;
2. at most 10% incomplete/unstopped claims among completed claims;
3. an oracle-unsupported completion-label rate greater than 20%; and
4. a two-sided 95% Wilson confidence interval whose lower bound is greater than 20%.

### H0

One or more H1 conditions are not met.

### H2 — alternative explanations

The observed unsupported rate may be substantially explained by missing execution records, empty/error patches, weak or incomplete benchmark tests, identifier inconsistency, dataset leakage, or adapter errors.

## Required source fields

The adapter must find and reconcile:

- `total_instances`
- `submitted_instances`
- `completed_instances`
- `resolved_instances`
- `unresolved_instances`
- `empty_error_patch_instances`
- `unstopped_instances`

Required count identities:

- `resolved_instances + unresolved_instances == completed_instances`
- `completed_instances == submitted_instances`
- all counts are non-negative integers
- `completed_instances <= total_instances`

A failed identity makes the record `UNVERIFIABLE`; it must not be silently repaired.

## Metrics

- completed claims
- oracle-supported claims
- oracle-unsupported claims
- unsupported completion rate
- 95% Wilson interval
- missing/incomplete rate
- completion-label precision relative to the supplied oracle
- four-state adapter coverage
- adapter parsing time and source-to-result line count

## Sensitivity analyses

1. Recalculate after excluding `empty_error_patch_instances` from the denominator, where this is arithmetically coherent. This is descriptive because empty/error patches may already be included among unresolved claims.
2. Compute how many currently unsupported claims would need to be reclassified as acceptable to reduce the rate to 20%.
3. Report the result if all `unstopped_instances` are treated as unsupported and if they are excluded.
4. Treat Policy B (agent natural-language self-report) as `UNTESTABLE HERE` unless the fixed file contains a ground-truthed self-report field.

## Stopping and decision rule

Analysis stops after the single fixed source is parsed, validated, and the predefined sensitivity analyses are produced. No additional source is added to obtain a preferred result.

- `SUPPORTED`: every H1 condition is met.
- `NOT SUPPORTED`: the record is valid and one or more H1 conditions fail.
- `INCONCLUSIVE`: the record is valid enough to inspect but sample size, missing evidence, or ambiguity prevents the predefined comparison.
- `BLOCKED`: the fixed source cannot be accessed or credibly parsed.

## Ethics, licensing, and data handling

Only public aggregate benchmark results are used. Hidden chain-of-thought, private trajectories, secrets, and personal data are excluded. The repository stores derived counts, immutable source location, Git blob SHA, and hashes rather than redistributing the full result file.
