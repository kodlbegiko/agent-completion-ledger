# v0.2.0 dogfooding protocol

## Repositories

1. `kodlbegiko/shipcheck` — TypeScript/Node release-consistency checker with documented lint, tests, and build.
2. `kodlbegiko/CSV-Snapshot` — Python CSV drift checker with documented tests and package build.

The external product repositories are not modified. Fixed adapters live under `examples/real-repositories/`, and CI checks out the real public repositories at the commit selected by GitHub Actions for that run.

## Controlled cases per repository

- `*-success`: repository-native files, tests, lint where applicable, and build must pass.
- `*-failure`: a deliberately false file assertion must produce `FAILED` without changing product behavior.
- `*-unverifiable`: missing blocking evidence or a disallowed executable must produce `UNVERIFIABLE`.

Controlled failures test status semantics. They are not presented as naturally occurring defects in Shipcheck or CSV Snapshot.

## Metrics

`scripts/dogfood.py` records contract line count, assertion count, total execution time, per-assertion timing, expected-state agreement, controlled false positives/negatives, number of `completed` claims corrected to another state, required manual setup steps, and human-adjudication limits.

## Adoption friction observed during integration design

- Each repository needs an explicit executable allowlist.
- Native dependency installation remains outside the evidence contract because contracts must not download remote code automatically.
- Full tests dominate runtime; file and JSON assertions add negligible work.
- Passing tests cannot establish product value or user satisfaction, so one human-adjudication item remains for both repositories.

Actual runner timings and statuses are produced by CI artifacts. They must not be replaced with invented local timings when the external repositories cannot be checked out in the current container.
