# v0.2.0 dogfooding protocol and measured results

## Repositories

1. `kodlbegiko/shipcheck` — TypeScript/Node release-consistency checker with documented lint, tests, and build.
2. `kodlbegiko/CSV-Snapshot` — Python CSV drift checker with documented tests and package build.

The external product repositories were not modified. Fixed adapters live under `examples/real-repositories/`; GitHub Actions checked out real public commits and ran their native quality commands.

## Controlled cases per repository

- `*-success`: repository-native files, tests, lint where applicable, and build must pass.
- `*-failure`: a deliberately false file assertion must produce `FAILED` without changing product behavior.
- `*-unverifiable`: missing blocking evidence or a disallowed executable must produce `UNVERIFIABLE`.

Controlled failures test status semantics. They are not presented as naturally occurring defects in Shipcheck or CSV Snapshot.

## Required human and setup work

Each run required three mechanical setup steps: check out the public repository, install its documented development dependencies, and run the contract. Contract authoring time was not independently timed and must not be inferred from execution time.

One substantive adjudication item remains for each repository: passing the selected tests and build does not establish whether the underlying product outcome is valuable or semantically complete.

## Adoption friction

- Each repository needs an explicit executable allowlist.
- Native dependency installation remains outside the evidence contract because contracts must not download remote code automatically.
- Full tests and builds dominate runtime; file and JSON assertions add negligible work in these runs.
- Repository-specific commands still require maintainer knowledge.
- The two tests demonstrate feasibility, not independent adoption or willingness to maintain contracts.

## Interpretation

Dogfooding supports the engineering claim that one schema and four states can run against two different real repositories and correctly distinguish controlled success, failure, and unverifiable cases. It does not estimate natural false-positive/false-negative rates, saved reviewer time, or user adoption.
